# Reference.md — эталон проекта «Портфолио Product Manager»

Документ фиксирует цель, референсы, требования к эталонному виду сайта, принятые решения и рабочий процесс.
Правило: любое решение по проекту сначала заносится сюда (разделы 4, 9 и 12), потом реализуется в коде.

Статус: сайт опубликован на https://marksvess.github.io/portfolio/ (раздел 14). Следующий этап — наполнить профиль данными из `Data/`, купить домен.
Дата создания: 2026-09-23. Последнее обновление: 2026-09-23.

---

## 1. Цель проекта

Сайт-портфолио продакт-менеджера, который:

1. Показывает **фото специалиста** и **короткое текстовое резюме** (кто, чем занимается, ключевые достижения, контакты).
2. Содержит **каталог mini app** — примеров продуктов и проектов. У каждого mini app есть:
   - страница с описанием (проблема, решение, роль автора, результат / метрики);
   - возможность **попробовать MVP**: либо ссылка на внешний сайт, либо раздел текущего сайта, где MVP запущен.
3. Позволяет владельцу **легко добавлять новые mini app** и **обновлять резюме** без переделки сайта.
4. Работает на **двух языках** (русский и английский) и открывается **из РФ и из США** без VPN.
5. Содержит **блог**, **форму обратной связи** и **аналитику посещений**.

Целевая аудитория: рекрутеры и нанимающие менеджеры (РФ и глобальный рынок), потенциальные партнёры и заказчики, коллеги по продуктовому сообществу.

Критерий успеха: посетитель за 30 секунд понимает, кто автор, и за один клик попадает в работающий MVP любого продукта.

Общие наблюдения по подборкам портфолио PM (sitebuilderreport, careerfoundry, underdog.io, aakashg.com):
- Большинство PM-портфолио сделаны на Squarespace, Webflow или Notion. Кастомный код встречается редко, и это возможность выделиться.
- Рекрутер читает не более трёх-четырёх кейсов. Качество важнее количества.
- Стандартная структура кейса: Проблема → Процесс → Результат с измеримыми метриками.
- Почти ни у кого нет **живых MVP внутри сайта**. Обычно это ссылки на Figma-прототипы, Loom-видео или внешние сайты. Встроенный работающий MVP — редкое преимущество.

### 2.2. Три лучших варианта и почему они лучше

#### 1. samdickie.me — эталон по позиционированию «PM, который делает продукты»

Почему лучше:
- Позиционирование «Product Manager & Maker» полностью совпадает с целью проекта: не только управляет, но и выпускает продукты.
- Раздел продуктов и материалов ведёт на **реальные живые артефакты** (шаблоны, гайды, AI-эксперимент), а не на описания в PDF.
- Есть повторяющиеся точки контакта: рассылка, консультации, соцсети. Сайт работает как воронка, а не как визитка.
- Чёткая иерархия главной: приветствие с иллюстрацией → шесть компетенций с иконками → свежие материалы → продукты → контакт.

Что берём: структуру главной страницы, блок компетенций, идею «продукты с живыми ссылками».
Что не берём: иллюстрацию вместо фото (у нас нужно реальное фото), избыток коммерческих CTA.

#### 2. rauno.me/craft — эталон по каталогу mini app

Почему лучше:
- Раздел Craft — это именно **каталог маленьких работающих штук**: сетка карточек с визуальным превью, названием, датой и ссылкой «View Prototype» / «View Production».
- В одной сетке живут разнотипные сущности (прототип, эссе, приложение), объединённые единым форматом карточки. Это решает нашу задачу: mini app может быть и внешней ссылкой, и разделом сайта, и текстовым кейсом.
- Датировка карточек показывает динамику: посетитель видит, что автор регулярно что-то выпускает.
- Минимум текста на уровне каталога, детали на уровне карточки. Не перегружает.

Что берём: модель карточки mini app (превью, название, дата, тип, кнопка «Попробовать»), сетку каталога.
Что не берём: чисто визуальный дизайнерский уклон; у нас на карточке должен быть виден продуктовый результат.

#### 3. mokoron.com — эталон по структуре «фото + резюме + кейсы» для PM

Почему лучше:
- Классическая, понятная рекрутеру структура: About с фото и биографией → Work с подразделами (проекты, исследования, выступления, сайд-проекты) → Resume → Contacts.
- Каждый проект: карточка на главной с коротким названием и переход на отдельную страницу с полным описанием. Именно так нужно устроить страницу описания mini app.
- Таймлайн опыта и шесть областей навыков с иконками дают быстрый скан профиля.
- Есть скачивание CV и ссылки на Telegram, LinkedIn, GitHub — контактный блок, который ожидают в РФ и за рубежом.

Что берём: структуру About, таймлайн опыта, шаблон страницы проекта (вводная, цели, вызовы, результат), контактный блок с CV.
Что не берём: отсутствие живых демо — мы это как раз добавляем.

### 2.3. Итоговая формула эталона

`samdickie.me` (позиционирование и главная) + `rauno.me/craft` (каталог mini app) + `mokoron.com` (структура About и страницы кейса) + встроенные живые MVP (уникальное преимущество, ни у кого из референсов нет).

## 3. Эталонная структура сайта

### 3.1. Карта страниц (двуязычная)

Английская версия живёт в корне (глобальная аудитория), русская — с префиксом `/ru/`. На каждой странице переключатель языка ведёт на ту же страницу другой локали.

```
/                     EN  Главная: фото, короткое резюме, компетенции, избранные mini app, контакты
/ru/                  RU  То же на русском

/about   /ru/about    Подробнее: биография, таймлайн опыта, навыки, ссылка на CV
/cv      /ru/cv       Резюме в печатном виде; «Сохранить как PDF» даёт актуальный CV
/apps    /ru/apps     Каталог mini app: сетка карточек, фильтр по типу и тегам
/apps/<slug>          Страница mini app: описание, метрики, роль, кнопка «Попробовать»
/apps/<slug>/demo/    MVP, запущенный внутри сайта (только для demoType = embedded)
/blog    /ru/blog     Блог: список статей, RSS
/blog/<slug>          Статья
/contact /ru/contact  Контакты и форма обратной связи
```

Встроенные MVP (`/apps/<slug>/demo/`) — отдельные статические приложения, не зависят от локали и от фреймворка сайта. Открываются по кнопке «Попробовать» в новой вкладке на весь экран, без iframe.

### 3.2. Главная страница, порядок блоков

1. Hero: фото, имя, должность, одно предложение о себе, две кнопки: «Смотреть продукты» и «Связаться».
2. Короткое резюме: 3–5 предложений или 3–4 ключевых достижения с цифрами.
3. Компетенции: 4–6 карточек с иконкой и одной строкой описания.
4. Избранные mini app: 3–4 карточки, ссылка «Все продукты».
5. Последние статьи блога: 2–3 карточки.
6. Контакты и ссылки на соцсети.

### 3.3. Модель данных mini app

Каждое mini app описывается одной записью на каждый язык (файл `src/content/apps/<lang>/<slug>.mdx`) с полями:

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `slug` | string | да | URL-идентификатор, одинаковый для обеих локалей |
| `title` | string | да | Название |
| `tagline` | string | да | Одна строка: что это и для кого |
| `cover` | image | да | Превью для карточки, 16:9 |
| `date` | date | да | Дата выпуска или последнего обновления |
| `status` | enum | да | `live` / `mvp` / `concept` / `archived` |
| `demoType` | enum | да | `external` (внешняя ссылка) / `embedded` (раздел сайта) / `none` |
| `demoUrl` | url | если external | Внешняя ссылка на MVP |
| `demoLanguages` | string[] | нет | На каких языках доступен сам MVP |
| `role` | string | да | Роль автора в проекте |
| `tags` | string[] | нет | Домены, технологии, методики |
| `problem` | markdown | да | Какую проблему решает |
| `solution` | markdown | да | Что сделано |
| `outcome` | markdown | да | Результат, метрики, выводы |
| `links` | list | нет | Репозиторий, статья, видео |
| `featured` | boolean | нет | Показывать на главной |

### 3.4. Модель данных профиля (резюме)

Файл `src/content/profile/<lang>.md` — единый источник для hero, About и страницы `/cv`:

| Поле | Описание |
|---|---|
| `name`, `title`, `location` | Имя, должность, город |
| `photo` | Путь к фото |
| `summary` | Короткое резюме для главной, 3–5 предложений |
| `bio` | Расширенная биография для About |
| `highlights[]` | 3–4 достижения с цифрами |
| `skills[]` | Компетенции: название, иконка, описание |
| `experience[]` | Таймлайн: компания, роль, период, достижения |
| `education[]` | Образование |
| `contacts` | Email, LinkedIn, Telegram, GitHub |

Обновление резюме = правка одного файла на каждый язык. Страница `/cv` собирается из этих данных с печатными стилями, PDF получается через «Печать → Сохранить как PDF».

### 3.5. Модель данных статьи блога

Файл `src/content/blog/<lang>/<slug>.mdx`: `title`, `description`, `date`, `tags`, `cover` (опционально), `draft`.

### 3.6. Страница mini app, порядок блоков

1. Заголовок, tagline, статус, дата, теги.
2. Кнопка «Попробовать MVP» (ведёт на внешний сайт или в `/apps/<slug>/demo/`), рядом ссылки на репозиторий и материалы.
3. Проблема → Решение → Результат (с метриками).
4. Роль автора и чему научился.
5. Навигация к соседним mini app.

### 3.7. Нефункциональные требования

- Адаптивность: мобильные устройства в приоритете, боковые отступы 16px, без горизонтального скролла.
- Производительность: Lighthouse ≥ 90 по всем категориям на главной и в каталоге.
- Доступность: контраст, alt-тексты, навигация с клавиатуры.
- Тёмная и светлая темы по системной настройке.
- SEO: Open Graph карточки для каждой страницы, `hreflang` для пар RU/EN, sitemap, RSS для блога.
- Добавление нового mini app: один файл описания на язык и одна картинка, без правок в остальном коде.
- Доступность из РФ и США без VPN: не использовать Cloudflare (проксирование), Vercel, Netlify.

## 4. Варианты технической реализации

### Вариант A. Astro + MDX + «острова» — ВЫБРАН

Стек: Astro 5, Content Collections (описания в MDX со схемой Zod), Tailwind CSS 4, shadcn/ui для интерактивных компонентов (React-острова), встроенный i18n-роутинг Astro, Keystatic как визуальная админка (локальный режим), хостинг GitHub Pages, свой домен.

Как устроено:
- Каждое mini app — MDX-файл на язык плюс обложка. Схема полей из раздела 3.3 проверяется на этапе сборки.
- Внешний MVP — просто `demoUrl`. Встроенный MVP — отдельное Vite-приложение в `apps/<slug>/`, собирается независимо, результат копируется в `dist/apps/<slug>/demo/`.
- Резюме, статьи и mini app редактируются через форму Keystatic на `localhost:4321/keystatic` или напрямую в файлах через Claude Code.

Плюсы:
- Нулевой JS по умолчанию на контентных страницах: быстрый сайт, Lighthouse 100 достижим.
- Строгая типизация контента: сломанное описание mini app не пройдёт сборку.
- MVP изолированы: ошибка в одном приложении не ломает сайт.
- Бесплатный хостинг, деплой по git push.

Минусы:
- Нет серверной части: форма и аналитика идут через внешние сервисы (раздел 9, вопросы 7).
- Если появится MVP с базой данных и пользователями, ему потребуется отдельный бэкенд (Supabase или VPS, раздел 10).

Почему выбран: у владельца сейчас приложения без бэкенда, в будущем в основном внешние ссылки. Сайт по сути контентный, а Astro лучший инструмент для контентных сайтов. Keystatic снимает барьер «не работал с Git».

### Вариант B. Next.js (App Router) + MDX + Supabase, хостинг Vercel — отклонён

Единое приложение для сайта и MVP с бэкендом, базой, авторизацией. Отклонён: избыточен для контентного сайта без бэкенда, а Vercel недоступен из РФ. Возвращаемся к нему, если появится 2+ MVP с реальными данными и пользователями (тогда самостоятельный хостинг на VPS, не Vercel).

### Вариант C. No-code: Webflow или Framer + внешние MVP через iframe — отклонён

Самый быстрый запуск, визуальный редактор. Отклонён: MVP внутри сайта только через iframe, платная подписка 14–29 $/мес, слабый сигнал «умею делать продукт», нет практики связки Figma → код, которую хочет владелец.

### Сравнение

| Критерий | A. Astro | B. Next.js | C. Webflow/Framer |
|---|---|---|---|
| Скорость запуска | средняя | средняя | высокая |
| Производительность сайта | максимальная | высокая | средняя |
| MVP без бэкенда внутри сайта | отлично | отлично | только iframe |
| MVP с базой и авторизацией | через внешний сервис | нативно | нет |
| Добавление mini app без кода | да, через Keystatic | возможно с админкой | да |
| Доступность из РФ на типовом хостинге | GitHub Pages: да | Vercel: нет | да |
| Стоимость хостинга | 0 | 0 на старте | 14–29 $/мес |
| Контроль дизайна | полный | полный | высокий в рамках платформы |

## 5. Визуальные ориентиры

- Тон: спокойный, профессиональный минимализм. Ближе к mokoron.com и emilkowal.ski, чем к kanesherwell.com.
- Дизайн-система: shadcn/ui (Figma-кит + код 1:1). Подробности в разделе 11.
- Типографика: одна гарнитура для заголовков, одна для текста, крупные заголовки, много воздуха. Шрифты с поддержкой кириллицы обязательны (например, Inter, Manrope, Onest).
- Цвет: нейтральная база + один акцентный цвет для кнопок «Попробовать».
- Карточка mini app: обложка 16:9, статус-бейдж, название, tagline, дата, теги.
- Фото: реальная фотография, не иллюстрация, в hero главной и на странице About.

## 7. Открытые вопросы

Вопросы 1–8 первой итерации закрыты (раздел 9). Домен, оплата, GitHub закрыты (раздел 13). Остаются:

1. Figma-кит: Obra shadcn/ui Community Edition (MIT, полный) или shadcncraft Free Starter (нативные Figma variables). Рекомендация — Obra. Владелец займётся Figma позднее, до этого сайт собирается на дефолтной теме shadcn/ui, токены подменяются потом.
2. План Figma: Starter (бесплатно, MCP через Framelink) или Professional Full seat (~16 $/мес). Рекомендация — Starter. Professional потребует зарубежной карты.
3. Зарубежная карта: нужна только для Figma Professional и Hetzner. Пока не требуется; вернуться к вопросу, если понадобится одно из двух.

## 9. Ответы на уточняющие вопросы и принятые решения

### Вопрос 1. Языки — оба

Решение: EN в корне сайта, RU под `/ru/`. Встроенный i18n Astro, контент в папках по локали, переключатель языка на каждой странице, `hreflang`.
Почему: английская версия в корне лучше для глобального поиска и рекрутеров за рубежом; русская версия полноценная, а не перевод-заглушка.
От владельца: тексты резюме и описаний на обоих языках (первый черновик перевода может сделать Claude Code, владелец вычитывает).

### Вопрос 2. Как добавлять контент, если не работал с Git

Решение: три уровня, от простого к сложному, все совместимы между собой.
1. **Claude Code как редактор.** Владелец пишет: «добавь mini app X, вот описание». Claude создаёт файлы, проверяет сборку, делает коммит. Это основной режим на старте.
2. **Keystatic в локальном режиме.** Запуск `npm run dev`, открыть `localhost:4321/keystatic`, заполнить форму: mini app, статья, резюме. Файлы сохраняются на диск. Бесплатно, без настройки OAuth.
3. **GitHub Desktop** для публикации: кнопки Commit и Push вместо командной строки. После push GitHub Actions собирает и выкладывает сайт автоматически.

Почему: сохраняем все плюсы git (история, откат, бесплатный хостинг), но убираем командную строку из ежедневной работы. Минимум, который нужно понять: репозиторий, коммит, push. Остальное закрывают инструменты.
От владельца: аккаунт GitHub, установить GitHub Desktop и Node.js LTS. Пошаговая инструкция появится в `README.md` при скаффолдинге.

### Вопрос 3. Какие MVP в приоритете

Решение: модель mini app поддерживает оба типа с первого дня, кнопка «Попробовать» выглядит одинаково.
- **Сейчас**: клиентские приложения без бэкенда. Каждое — отдельная папка `apps/<slug>/` (Vite + любой фреймворк), собирается независимо, результат попадает в `/apps/<slug>/demo/`. Кнопка открывает его в новой вкладке на весь экран.
- **В будущем**: внешние ссылки на чужие продукты (`demoType: external`). Страница описания остаётся на сайте, кнопка ведёт наружу. Для чужих продуктов в поле `role` явно указывать роль и границы ответственности.
- **Если появится MVP с бэкендом**: выносить в отдельный сервис (Supabase или VPS), сайт только ссылается. Сайт-портфолио никогда не зависит от бэкенда MVP.

Почему: изоляция. Портфолио всегда открывается, даже если конкретный MVP сломан или закрыт. Внешние продукты не требуют ничего, кроме описания.

### Вопрос 4. Домен и хостинг с доступом из РФ и США

Решение по хостингу: **GitHub Pages** для сайта, собственный домен, деплой через GitHub Actions.
Почему:
- Бесплатно, стабильно, открывается из РФ и США без VPN (в отличие от Cloudflare-проксирования, Vercel и Netlify, см. источники в разделе 6).
- Сборка и публикация автоматические после push, сервер администрировать не нужно.
- Статический сайт Astro переносится на любой хостинг за час, если условия изменятся. Резервный путь описан в разделе 10.
- Сервер сейчас не нужен: у сайта нет бэкенда. Арендовать VPS есть смысл, когда появится MVP с базой или своя форма/аналитика (раздел 10).

Решение по домену: зона `.com` (нейтральна для обеих аудиторий) или `.dev`. Не `.ru` (сужает восприятие за рубежом) и не `.io`.
Регистратор: зависит от карты. Зарубежная карта — Porkbun или Namecheap (10–15 $/год). Российская карта — reg.ru или Timeweb, они регистрируют `.com`. DNS оставить у регистратора, без проксирования через Cloudflare.
От владельца: выбрать имя домена (вопрос 7.1), сообщить тип карты (вопрос 7.2).

### Вопрос 5. Фото, резюме и CV, которые нужно обновлять

Решение: резюме — данные, а не документ. Один файл профиля на язык (раздел 3.4) питает hero, About и страницу `/cv`. PDF-версия CV генерируется из `/cv` через печать в браузере, отдельный файл поддерживать не нужно.
Почему: обновление резюме сводится к правке одного файла, версии RU и EN не расходятся, PDF всегда актуален.
От владельца: фото в высоком разрешении (квадрат или портрет, минимум 1200 px по короткой стороне), текущие тексты резюме и CV в любом формате. Claude Code разложит их по полям профиля, владелец вычитает.

### Вопрос 6. Минимализм и практика связки Figma + Claude Code

Решение: дизайн-система **shadcn/ui**, потому что у неё есть бесплатные Figma-киты с переменными и код-компоненты 1:1. Полный пайплайн и чеклист для владельца в разделе 11.
Почему shadcn/ui, а не Material или Untitled UI: компоненты в Figma и в коде совпадают по именам и вариантам, токены Tailwind заложены в Figma Variables, минималистичный стиль по умолчанию, работает в Astro через React-острова.

### Вопрос 7. Блог, форма обратной связи, аналитика

- **Блог**: Content Collection `blog`, двуязычный, RSS, теги. Статьи в MDX, редактируются через Keystatic или Claude Code.
- **Форма обратной связи**: **Web3Forms** (бесплатно, до 250 отправок в месяц, письма на email, без бэкенда). Запасной вариант — Formspree (50 бесплатно, далее 10 $/мес). Рядом с формой всегда прямой email и Telegram, чтобы контакт не зависел от сервиса.
- **Аналитика**: **Umami Cloud, план Hobby** (бесплатно, 100 000 событий/мес, 3 сайта, 6 месяцев хранения). Без cookie-баннера, GDPR-совместимо, скрипт лёгкий. Опционально добавить Яндекс.Метрику для вебвизора по РФ-аудитории.

Почему: все три работают на статическом сайте, доступны из РФ и США, бесплатны на старте.

## 10. Хостинг и домен: детали и резервный план

### Основной контур
- Репозиторий на GitHub → GitHub Actions собирает Astro и встроенные MVP → публикация в GitHub Pages → свой домен через CNAME-запись у регистратора → HTTPS от GitHub автоматически.

### Проверка доступности
После запуска проверять открытие сайта из РФ (без VPN, мобильный и домашний интернет) и из США (через сервисы проверки, например, check-host.net). Повторять после смены хостинга или DNS.

### Резервный план, если GitHub Pages станет недоступен из РФ
- Собранная папка `dist/` — обычные статические файлы. Переезд на VPS в Европе (Hetzner, Финляндия или Германия) с Caddy или Nginx занимает около часа. Деплой из GitHub Actions по SSH/rsync.
- При оплате российской картой — Timeweb Cloud или Selectel, дата-центры в РФ и Нидерландах.
- Coolify на VPS даёт git-деплой одной кнопкой, если захочется PaaS-опыт без Vercel.

### Когда брать VPS
- Появился MVP с базой данных, авторизацией или серверной логикой.
- Захотелось свою форму обратной связи (например, в Telegram-бот) или самостоятельно размещённый Umami.
- GitHub Pages перестал открываться из РФ.

## 11. Дизайн-система: связка Figma ↔ Claude Code

### Принцип
Единый источник истины — **дизайн-токены** (цвета, типографика, отступы, радиусы). Они живут в Figma Variables и экспортируются в репозиторий как JSON. Код читает токены, а не «срисовывает» макеты. Компоненты в Figma и shadcn/ui в коде совпадают по именам.

### Пайплайн
1. **Figma**: скопировать бесплатный кит shadcn/ui в свой файл (Obra Community Edition или shadcncraft Free Starter). Настроить свои токены: акцентный цвет, нейтральная палитра, шрифт с кириллицей, радиусы.
2. **Экспорт токенов**: плагин Tokens Studio (бесплатный уровень) → файл `design/tokens.json` в репозитории. Обновляется при каждом изменении в Figma.
3. **Код**: скрипт превращает `tokens.json` в CSS-переменные для Tailwind 4 (`@theme`) и shadcn/ui. Claude Code запускает его командой `npm run tokens`.
4. **Макеты**: три ключевых экрана в Figma — главная, каталог mini app, страница mini app (десктоп + мобильный). Компоненты только из кита.
5. **Figma → Claude Code**: Claude читает макет через Figma MCP и собирает страницы из shadcn/ui-компонентов с токенами. Бесплатный путь — Framelink Figma MCP по персональному токену Figma REST API (работает на Starter). Платный путь — официальный Figma MCP на Professional.
6. **Обратная связь**: если в коде понадобился компонент или токен, которого нет в Figma, сначала добавляется в Figma, потом в код. Так дизайн-система остаётся источником истины.

### Что требуется от владельца
- [ ] Аккаунт Figma (Starter достаточно для начала).
- [ ] Скопировать выбранный кит shadcn/ui в свой файл, назвать `Portfolio DS`.
- [ ] Задать 4 группы токенов: цвета (фон, текст, акцент, границы для светлой и тёмной темы), шрифты (заголовок и текст с кириллицей), отступы (шкала 4/8/12/16/24/32/48/64), радиусы.
- [ ] Установить плагин Tokens Studio, выполнить первый экспорт в `design/tokens.json`.
- [ ] Собрать три ключевых экрана из компонентов кита (можно грубо, Claude Code доведёт).
- [ ] Создать персональный токен Figma (Settings → Security → Personal access tokens, права только на чтение файлов) и сохранить его локально в `.env`, не в репозитории.
- [ ] Поделиться ссылкой на файл Figma в чате с Claude Code.

### Что делает Claude Code
- Настраивает Framelink Figma MCP в проекте.
- Пишет скрипт конвертации токенов, подключает shadcn/ui к Astro.
- Собирает страницы по макетам, сверяет с макетом скриншотами в браузере.
- Предлагает правки в Figma, если в макете не хватает состояний (hover, пустой каталог, длинные заголовки на русском).

## 12. Рабочий процесс владельца

### Подключение GitHub Desktop (один раз)
1. File → Add local repository (или «Add an Existing Repository from your local drive»).
2. Указать папку `X:\Claude\Portfolio`, нажать Add repository.
3. **Не нажимать** «Clone marksvess/portfolio»: это создаст вторую копию проекта в другой папке, и правки разъедутся.
4. Проверка: вверху Current repository = `portfolio`, Current branch = `main`, во вкладке History виден первый коммит.

### Основные действия в GitHub Desktop
- **Changes** — список изменённых файлов. Внизу слева поле Summary (описание изменения) и кнопка Commit to main.
- **Push origin** — отправить коммиты на GitHub, после этого сайт пересобирается сам.
- **Fetch / Pull origin** — забрать изменения с GitHub, если правки делались в другом месте (например, Claude Code уже сделал push).
- **History** — все коммиты; правый клик по коммиту → Revert changes откатывает его.
- Если коммит сделал Claude Code, в Changes будет пусто, а на кнопке появится Push origin с числом коммитов. Достаточно нажать её.

### Проблема: «Invalidated account token» каждые несколько минут (2026-09-23)
Симптом: GitHub Desktop выходит из аккаунта примерно через 5 минут после входа, в логе `Bad credentials`. Вход для командной строки при этом работает.
Вероятные причины: антиспам-проверка нового аккаунта GitHub (создан в тот же день, API частично скрывает репозиторий) или смена IP через VPN (AmneziaVPN) между входом в браузере и работой приложения.
Что делать:
1. github.com → Settings → Emails: почта подтверждена. Проверено 2026-09-23: метка Verified, вход через Google, причина исключена. Рекомендовано включить «Keep my email addresses private».
2. github.com/settings/security-log: найти события `oauth_authorization.destroy` для GitHub Desktop, там видна причина отзыва.
3. Войти в Desktop заново с одинаковым состоянием VPN для браузера и приложения (либо оба через VPN, либо оба без).
4. Если на github.com есть баннер об ограничении аккаунта — обращение в support.github.com.
Обходной путь: коммиты в Desktop работают без входа; push делает Claude Code или команда `git -C X:/Claude/Portfolio push`.

### Добавить mini app
1. Собрать MVP в `apps/<slug>/` (или подготовить внешнюю ссылку).
2. `npm run dev`, открыть `http://localhost:4321/keystatic` → Products EN → Add, затем Products RU → Add с тем же Slug. Загрузить обложку. Или сказать Claude Code: «добавь mini app …».
3. Проверить локально: `http://localhost:4321/apps/<slug>/`.
4. GitHub Desktop → Commit → Push. Через 2–3 минуты страница в продакшене.

### Обновить резюме
1. Keystatic → Profile → правка полей на RU и EN. Или прислать Claude Code новый текст.
2. Проверить `/about` и `/cv`, при необходимости сохранить PDF из `/cv`.
3. Commit → Push.

### Написать статью
1. Keystatic → Blog → New. Или черновик в чате с Claude Code.
2. Commit → Push. RSS обновится сам.

### Изменить дизайн
1. Правка токенов или компонентов в Figma.
2. Экспорт токенов через Tokens Studio → `design/tokens.json`.
3. `npm run tokens`, проверить сайт локально, Commit → Push.

### Личные данные: папка `Data/`

Структура:
```
Data/
  README.md     что и куда положить, требования к фото
  photo/        исходное фото (portrait.jpg, min 1200 px по короткой стороне)
  resume/       resume-ru.md, resume-en.md (или docx/txt)
  cv/           текущие CV в PDF/DOCX
```

Правила:
- `Data/` исключена из git через `.gitignore`. В репозиторий попадают только обработанные материалы: сжатое фото в `public/`, тексты в полях профиля.
- Телефон, адрес, дата рождения и другие идентифицирующие данные на сайт не переносятся без явного согласия владельца.
- Источник истины для текста резюме после первого переноса — файлы профиля сайта (раздел 3.4), а не `Data/`. `Data/` остаётся архивом исходников.

### Figma: отложено

Владелец займётся Figma позднее. Токены по умолчанию лежат в `src/styles/tokens.css`, именно этот файл будет заменяться экспортом из Figma. До этого сайт собирается на дефолтной теме shadcn/ui с нейтральной палитрой и шрифтом с кириллицей. Пайплайн раздела 11 остаётся в силе: когда токены появятся в Figma, они подменяют дефолтные без переделки компонентов.
